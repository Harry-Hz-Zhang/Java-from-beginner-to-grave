# B 组讲解：数据访问层

这一组四个模块（05 到 08）表面上看是在讲四个工具：BaseMapper、审计字段、手写 SQL、Flyway。实际上它们回答的是同一个问题——数据访问层的复杂度分布在哪些地方，以及什么情况下该用哪种手段。

## 一、先建立一个判断框架

很多人学 MyBatis-Plus 的方式是把十七个方法背下来，然后所有需求都用 `selectList` 加条件构造器硬凑。这样能跑，但会写出又长又慢又难维护的代码。

正确的判断框架是按「复杂度来自哪里」分四类。

第一类，单表按主键或少量条件增删改查。这类交给 `BaseMapper`，一行代码都不写。

第二类，需要统一维护的横切字段，例如创建时间、更新人、版本号、删除标记。这类交给注解加拦截器，让框架在每次读写时自动处理，业务代码不用管。

第三类，需要加锁、需要一次往返改多列、需要可选条件组合加排序分页。这类必须手写 SQL，条件构造器会把代码写得很长而且不好控制。

第四类，表结构本身的演进。这类不是代码问题，是工程协作问题，交给 Flyway。

四个模块对应的就是这四类。你以后拿到一个新需求，先判断它属于哪一类，再决定写什么代码。

## 二、串讲：一条任务记录的完整生命周期

假设要支持「创建任务、按状态筛选列表、改配置、删除、后来又加一个模型字段」。

创建时，你 new 一个 `TaskDO`，填业务字段，调用 `mapper.insert(task)`。看起来你只做了一件事，实际上框架做了四件：根据 `@TableName` 找到表名，根据非 null 字段拼出 INSERT 语句，让 `MetaObjectHandler` 填入创建时间、版本号 0、删除标记 false，最后把数据库生成的自增 id 回填到对象上。

筛选列表时，条件是「状态等于 RUNNING 且名字以镜像开头，按 id 倒序，第 2 页每页 10 条」。这里出现分水岭。如果只有前两个条件，用 `Wrappers.lambdaQuery()` 最干净；但一旦有分页，你就得注意这个项目没有注册分页插件，`selectPage` 不会真正分页，必须手写 `LIMIT OFFSET`。

改配置时，你想只改模型名和 API Key，不想动其他列。这里的关键是 `@TableField(updateStrategy)` 的策略。默认 `NOT_NULL` 表示「只更新我设了值的列」，这正好符合需求。但如果你想把 `systemPrompt` 清空成 null，默认策略会跳过它，必须给这个字段标 `ALWAYS`。

并发修改时，两个请求同时读到 version=3，都改成 4。乐观锁拦截器让第二条 UPDATE 带上 `WHERE version = 3`，影响行数为 0，你的代码据此判断「有人先改了」，可以重试或报冲突。这个机制只有在注册了 `OptimisticLockerInnerInterceptor` 之后才生效，注解本身不做任何事。

删除时，`deleteById` 实际执行的是 `UPDATE ... SET deleted = 1`。之后所有查询自动追加 `deleted = 0`，业务代码完全感知不到数据还在表里。但也因此，你必须清楚「表会一直变大」这个代价。

几个月后产品要加模型字段。这时不能去改 V1 脚本，只能新增一个脚本（生产的模型配置列就是 V11 加的）。因为 V1 已经在所有环境执行过，Flyway 记录了它的校验和，改动一个字符就会让所有环境启动失败。而且那个新脚本不能简单地「加一个非空列带默认值」——生产 V11 的做法是三步：先 `ADD COLUMN ... DEFAULT NULL`，再 `UPDATE` 回填，最后 `MODIFY COLUMN ... NOT NULL`。三步走的好处是回填过程看得见，中间失败也能重跑。

这条生命周期把所有细节串起来了。你会发现真正需要判断的地方只有三处：分页、更新策略、并发控制。

## 三、完整用法清单

### BaseMapper 的十七个方法

| 分类 | 方法 | 说明 |
| --- | --- | --- |
| 插入 | `insert` | 返回影响行数，主键回填到对象 |
| 按主键删 | `deleteById` | 有 `@TableLogic` 时变成逻辑删除 |
| 按条件删 | `delete(Wrapper)` | 传 null 会删全表，生产禁用 |
| 批量删 | `deleteBatchIds` | 内部拼 IN |
| 按主键改 | `updateById` | 只更新非 null 字段（受策略控制） |
| 按条件改 | `update(entity, wrapper)` | 配合 wrapper 做批量更新 |
| 按主键查 | `selectById` | 最常用 |
| 批量查 | `selectBatchIds` | 内部拼 IN |
| 条件查列表 | `selectList(wrapper)` | 最常用 |
| 条件查单个 | `selectOne(wrapper)` | 多于一条会抛异常 |
| 条件查数量 | `selectCount(wrapper)` | 返回 Long |
| 条件查 Map | `selectMaps(wrapper)` | 只取部分列时省内存 |
| 条件查单列 | `selectObjs(wrapper)` | 只要一列值 |
| 分页 | `selectPage` | 需要分页插件，这个项目没有 |

### 条件构造器的方法

`eq`、`ne`、`gt`、`ge`、`lt`、`le`、`between`、`notBetween`、`like`、`notLike`、`likeLeft`、`likeRight`、`in`、`notIn`、`isNull`、`isNotNull`、`orderByAsc`、`orderByDesc`、`groupBy`、`having`、`and`、`or`、`nested`、`last`。

每个条件方法都有一个首参为 boolean 的重载，条件为 false 时该片段不拼接。这比在外面写 if 更简洁，也是生产代码里的常见写法。

### FieldStrategy 的取值

| 值 | 更新时的行为 | 典型用途 |
| --- | --- | --- |
| `NOT_NULL` | 字段为 null 就不出现在 SET 里（默认） | 大部分业务字段 |
| `ALWAYS` | 无论是否为 null 都写入 | 需要能清空的字段 |
| `NEVER` | 永远不出现在 SET 里 | 创建时间、uuid 等不可变字段 |
| `NOT_EMPTY` | 字符串空串也跳过 | 老项目常见 |

### 注解 SQL 的要点

| 要点 | 说明 |
| --- | --- |
| `#{x}` | 预编译占位符，防注入 |
| `${x}` | 字符串拼接，仅用于动态表名、排序列 |
| `@Param` | 建议写；本项目因 `-parameters` 默认开启，不写也能按形参名解析（生产两种写法都有，13 处没写） |
| `<script>` | 注解里写动态 SQL 的入口 |
| `<if test>` | test 是 OGNL 表达式，判空写 `!= null` |
| `<foreach>` | 拼 IN 列表 |
| `@Options(useGeneratedKeys)` | 注解插入时回填主键 |

### Flyway 的要点

| 概念 | 说明 |
| --- | --- |
| 命名 | `V{版本}__{描述}.sql`，两个下划线 |
| 顺序 | 按版本号，不按文件名 |
| 校验和 | 已执行脚本不可修改 |
| `validate-on-migrate` | 启动时校验，生产必须开 |
| `clean-disabled` | 禁止清库，生产必须开 |
| `baseline-on-migrate` | 接管已有数据库时用；本项目未启用 |

## 四、六个常见误区

第一个，以为 `@TableLogic` 之后 `selectCount` 还能统计到已删除数据。实际上它也会自动加 `deleted = 0`，想统计全部必须绕过框架手写 SQL。

第二个，以为 `@Version` 加上就自动生效。没有拦截器它什么都不做，这是「注解存在但行为不存在」的典型。

第三个，以为 `updateById` 会把对象所有字段都写一遍。它只写非 null 的那些，这个默认值救过很多人，也坑过想清空字段的人。

第四个，在 `where` 条件里用 `${}` 拼用户输入，等于把注入漏洞写在代码里。

第五个，把逻辑删除和唯一索引一起用，指望「删掉的名字可以再用」。实际上唯一索引如果只建在名字上，第二次插入同一个名字会失败，必须把 `deleted` 一起放进索引。

第六个，改已经上线的迁移脚本。这是团队协作里破坏力最大的操作，它会让所有人本地启动失败，而且错误信息（校验和不一致）不容易一眼看出原因。

## 五、自测题

1. `BaseMapper` 的十七个方法里，哪些在加了 `@TableLogic` 之后行为会变？变成什么？
2. `@TableName` 不写时，框架怎么猜表名？为什么几乎一定猜错？
3. 一个查询要「按状态筛选、按名字模糊、按时间倒序、分页」，这个项目里应该怎么实现？为什么不用 `selectPage`？
4. `@TableField(updateStrategy = NEVER)` 和 `FieldStrategy.ALWAYS` 各解决什么问题？各举一个生产项目里的字段。
5. 乐观锁冲突时，你的代码会看到什么返回值？应该怎么处理？
6. `#{userId}` 和 `${userId}` 在执行层面的区别是什么？
7. 两个参数的方法不加 `@Param` 为什么也能跑？什么情况下会真的报错？
8. `MetaObjectHandler` 对手写的 `@Update` 语句生效吗？为什么？
9. 表结构要加一个字段，为什么不能改 V1？如果改了会发生什么？
10. 逻辑删除的表想加唯一索引，索引应该建在哪几列上？

## 六、学完这一组之后

你应该能独立判断：这个需求该用 `BaseMapper`、该用条件构造器、还是该手写 SQL；以及写完之后，哪些字段会被自动填、哪些不会被自动填。
