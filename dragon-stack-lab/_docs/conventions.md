# 编写纪律

这份文件规定这个实验室里每个 demo 必须遵守的规则。规则存在的目的只有一个：让每个模块只演示一个知识点，并且能被你五分钟内读懂。

## 一、代码行数

每个模块的 Java 代码总量（统计时排除注释行、空行、`import` 语句）基准是 50 行。允许超出，但只有两种理由成立：

第一种，**对照演示**。一个知识点在框架里有多种分支，而「分支之间的差别」正是要学的内容。比如 JSON-RPC 的错误帧、超时、通知、半帧、stderr 五种情况，少演示一种就少一个坑，合并进一个方法反而看不懂。这种情况超出是必要的。

第二种，**为了不撒谎**。如果为了压行数把「生产用两列存 hash 和 salt」简化成「只存一列」，代码短了，但学到的是错的。宁可多写十行把差异摆出来。

不允许的理由是第三种：为凑行数加入与知识点无关的 getter、setter、日志和判空。那些代码会稀释注释里真正有用的语法说明。

超出的模块必须在 README 的「行数说明」小节写明超了多少、超出的部分是注释还是对照分支、为什么不能删。没有写说明的超限视为不合格。

这个纪律的意义在于防止 demo 逐渐长成半个业务系统——读它的时候需要先理解业务背景，那就失去了「五分钟读懂一个知识点」的价值。

## 二、注释四段式

每个关键 API 的注释必须回答四个问题，缺一个都算不合格。

第一个问题是「它是什么」，也就是这个注解或这个类在框架里承担什么角色。第二个问题是「语法怎么写」，说清必填参数、可选参数和常见写法。第三个问题是「为什么这里需要它」，也就是如果删掉它会发生什么。第四个问题是「生产项目在哪用了」，必须给出具体类名，不能只写「生产里有」。

前三个问题解决「看不懂」，第四问解决「学完用不上」。你会发现生产项目里有些写法看起来多余，比如 `@TableField(updateStrategy = FieldStrategy.NEVER)`，只有把第四问答出来，你才知道那是为了防止创建时间被后续更新覆盖。

## 三、命名与结构

模块目录用两位数字前缀加短横线连接的主题名，例如 `05-mybatis-crud`。数字前缀决定 Maven 构建和文件浏览器的排序，让学习顺序自然呈现。主题名用英文小写，避免中文路径在部分终端和持续集成环境下的编码问题。

包名统一为 `com.harry.lab.<主题>`，与模块名一一对应，方便你在 IDE 里按包定位模块。

每个模块固定包含四个部分。`pom.xml` 只声明这个知识点真正需要的依赖。`src/main/java` 放一到三个类。`src/main/resources` 放配置或建表脚本，没有就不建空目录。`README.md` 写清这个 demo 演示什么、怎么运行、观察什么现象、对应生产项目哪个文件。

## 四、能运行

每个模块要么能通过 `mvn -pl <模块名> test` 跑通，要么能在 README 里用一条命令启动并说明预期输出。纯讲解、跑不起来的示例不收录，因为跑不起来的代码无法验证你的理解是否正确。

依赖外部服务（Redis、Docker、MySQL 容器）的模块，必须在 README 顶部用一行醒目说明写出前置条件，并且保证缺少这些条件时编译仍然通过，只是运行失败。

## 五、版本锁定

Spring Boot 4.1.1、Java 21、MyBatis-Plus 3.5.18、MapStruct 1.6.3，全部与你生产项目一致。任何升级都必须同时检查 `harness_saas` 和 `dragon_harness` 是否也升级了，否则你学到的是与线上不同的 API。

**工程锁定 JDK 21。** 根 `pom.xml` 的 `<java.version>21</java.version>` 经 Spring Boot parent 翻译成 `maven.compiler.release=21`，编译目标固定。

本机 `~/.zshrc` 已配 `export JAVA_HOME=$(/usr/libexec/java_home -v 21)`，交互终端里直接 `mvn` 就是 21。只有非交互环境（脚本、CI、部分 IDE 运行器）才需要显式带上，因为那些环境不加载 `~/.zshrc`。

判断依据只有一条：`mvn -v` 里的 `Java version`。从 JDK 23 起注解处理默认关闭（`-proc:none`），Lombok 与 MapStruct 会静默失效——不是编译报错，而是在奇怪的位置失败。为防这种情况，根 `pom.xml` 的 compiler 插件显式写了 `<proc>full</proc>`，即使在更高 JDK 上也保持注解处理开启。

## 六、不谎称生产用法

这条规则是审查之后加的，也是这份文件里最重要的一条。

写「对应生产项目的位置」时，**必须真的打开那个文件看到那一行**，不能凭印象推断「生产应该也这么写」。审查发现过三十多处这样的错误：

- 说生产用 `@Primary` 消歧，实际主代码零处，用的是 `@Bean(name=)` + `@Qualifier`；
- 说生产用 `@Async`，实际零处，异步走虚拟线程；
- 说生产用 `CompletableFuture` 的组合方法，实际全仓零命中，是手建 future + 虚拟线程；
- 说生产控制器测试用 `@WebMvcTest`，实际零处，是 `@SpringBootTest` + `@AutoConfigureMockMvc`；
- 说生产固定开 `redirectErrorStream`，实际零处，是用两个虚拟线程分别 drain。

这类错误的危害比「漏讲」大得多。漏讲你知道自己不会；写错了你会照着去生产代码里找，找不到就怀疑自己没看懂。

所以每个模块的用法清单里，除了「生产在哪用」，还要标出**「生产未用」**的条目。这个标注和正面清单同样重要——它回答的是「网上那种写法在这个项目里为什么行不通」。

判断一个用法是「生产未用」还是「漏写了」，方法只有一个：去生产仓库 grep，看到零命中才能写「未用」。grep 过才有资格下结论。
